# M6 — Development-Only Ground Glass Presentation

## Decision

M6 provides a native WebGPU Architecture Rise presentation path that displays the completed M5 B1 Far/Near research composite through the existing shared Ground Glass Stage. M6D adopts the **Opaque Final Presentation Contract** (`m6d-opaque-presentation-v1`): M5 consumes Near coverage while composing final RGB and writes alpha one; M6 applies RGB presentation operations and writes the opaque canvas output. The M6C source-alpha observation remains `alpha-observable-contract-different`; under the now-explicit opaque output requirement, final-output conformance is `final-output-conformant` and the development-only Architecture Rise M6 boundary is `architecture-implemented`. Photographic quality remains **quality-unqualified**, no M5Q threshold or Q1–Q7 result changes, M7 has not started, and production WebGPU remains disabled.

The native run and compact measurements are in [GROUND_GLASS_M6_PRESENTATION_REPORT.json](GROUND_GLASS_M6_PRESENTATION_REPORT.json). Full screenshots and the compressed GPU readback remain in ignored Playwright output.

## Development activation

Use the development server with both pilot gates enabled:

```bash
VITE_GROUND_GLASS_WEBGPU_RAW_PILOT=true \
VITE_GROUND_GLASS_WEBGPU_M6_PRESENTATION=true \
npm run dev
```

Open `/simulator/free/architecture-rise?rttDiagnostics=1` in a browser with native WebGPU enabled. M6 activates automatically for this exact scene when the development build has both documented pilot flags enabled; there is no public renderer selector. Confirm the pilot reports `data-mounted-renderer-family="webgpu-renderer"`, `data-actual-execution-api="webgpu"`, `data-presentation-mode="m6-experimental-dof"`, `data-presentation-source="m5-research-composite"`, and `data-presentation-status="completed"`. To return to the existing WebGL path, stop the server and restart without the M6 and Raw pilot flags.

The build-time gate requires all three conditions: `import.meta.env.DEV`, `VITE_GROUND_GLASS_WEBGPU_RAW_PILOT === "true"`, and `VITE_GROUND_GLASS_WEBGPU_M6_PRESENTATION === "true"`. M6 presentation requests are limited to the exact Architecture Rise scene identity and bounds and exclude Raw Debug. A verified M6-capable pilot session may start on Raw Debug, but other scenes stay on the existing WebGL host. The compatibility records attest implementation only; `qualityQualification` remains `unqualified`.

## Render path and ownership

The adapter keeps the existing M3 scene target, M4 physical CoC and validity targets, and M5 gather/B1/research-composite targets. M6 uses one fullscreen presentation node that samples the already-composited M5 target and applies display orientation, global throughput, natural illumination, and physical coverage before rendering to the canvas. It does not re-blend Near, re-run B1, add a render target, or add a second fullscreen pass. M5 remains the owner of its optical targets; the WebGPU adapter owns and disposes the M6 presentation material and geometry.

The final display only publishes a completed M6 frame after the matching M4 and M5 requests have completed for the same request, channel, scene, and renderer generation and the M6 render plus queue completion succeed. Initialization failure selects the existing host fallback. Presentation or final-display failure cannot be reported as completed M6 output. A held presentation that becomes stale after resize is discarded. These are bounded M6 controls, not the broader M7 device-loss and retry matrix.

## Coordinates and optical effects

- Raw and Upright use the established WebGPU render-target orientation transform. The asymmetric native sample gave mean RGB error 3.59 for the expected 180-degree correspondence, versus 44.06 for a horizontal-only flip and 52.39 for a vertical-only flip.
- Focus Loupe reuses the shared Stage inspection window and the existing camera source crop. Native center and panned captures changed the source crop while retaining the canonical physical window contract; resize regenerated the output at 394×315 with a 256×205 internal target in the final low-quality state.
- The presentation node maps each sampled source coordinate through the cropped physical film window before evaluating coverage and illumination. It reuses canonical coverage and natural-illumination state, including shifted circles and conics. Pure reference tests cover offset signs in both axes, combined offsets, feathering, conic coverage, crop, orientation, disabled coverage, and Raw Debug bypass.
- Global throughput uses `resolveGroundGlassRelativeIlluminance()`. In the native run the reported gain increased from 0.2416 at f/22 to 3.7293 at f/5.6. Natural illumination and coverage were both reported applied for the captured optical state.
- Raw Debug remains the M3 Raw target diagnostic path and does not receive M6 DOF, coverage, or natural illumination.

The registered M6-eligible Architecture Rise scene does not provide a physical film grid; its visible grid is decorative CSS and has no physical spacing. M6B addresses the testability gap with a controlled fixture that uses the actual presentation node and shared Stage, and its 14-capture physical-overlay matrix passed the declared per-capture limits. That evidence is fixture-scoped and does not claim that the registered scene itself has a physical grid.

## Color and comparison boundary

The M3 scene and M5 optical targets are sampled as unencoded linear values (`NoColorSpace`). The M6 TSL expression multiplies linear RGB and returns `source.a`; the actual `MeshBasicNodeMaterial` is opaque (`transparent=false`, `opacity=1`, `NormalBlending`). Three.js r186's opaque node-material path writes alpha one, as confirmed by M6C native RGBA8 readback. Under the M6D contract, `source.a` is an intermediate expression value, while the final material output and visible canvas are opaque. The WebGPU renderer writes to its sRGB canvas output; tone mapping is disabled. M6 does not encode sRGB in the presentation node. Unit controls cover black, white, middle gray, saturated and low-intensity patches and the linear-to-sRGB transfer function. See [GROUND_GLASS_M6C_ALPHA_CONFORMANCE.md](GROUND_GLASS_M6C_ALPHA_CONFORMANCE.md) for the measured source-versus-target alpha contract and [GROUND_GLASS_M6D_OUTPUT_CONTRACT_ADR.md](GROUND_GLASS_M6D_OUTPUT_CONTRACT_ADR.md) for the accepted stage semantics.

The WebGL and M6 screenshots are both 514×412, but they are not a parity result: mean sRGB luminance was 108.27 for WebGL and 158.86 for M6; 207,557 pixels changed and mean absolute channel error was 55.04. M6 also differed from M3 Raw (207,390 changed pixels; mean absolute channel error 24.47). These comparisons show the candidate output is visible and distinct. They do not establish which result is optically correct. M6B provides the scoped native physical-overlay and canvas RGB oracles; M6C separately measures alpha on an alpha-capable target.

## Raw-first M6 session provisioning — Review-Fix Round 1

M6 capability is authorized only in a development build with both the Raw pilot and M6 presentation flags set to the exact string `"true"`. The session-level provisioning decision additionally requires the exact Architecture Rise identity and bounds, selected WebGPU, and an observed `WebGPURenderer` using native WebGPU. This decision is independent of the first frame's Raw Debug value. It allocates the M4 physical CoC/validity resources and the M5 gather/B1/composite resources so a later M6 request in the same renderer generation has its inputs.

Provisioning does not enable pass execution. Raw Debug keeps the M3 scene-target display path: its accepted frame has no M4 or M5 optical passes and no completed M6 presentation. When a non-Raw M6 request arrives, M4, M5, and M6 execute for that request and their completed diagnostics must match its request, channel, scene, and renderer generation. Raw/M6 mode changes preserve the pilot session and renderer generation; the existing adapter cleanup owns and disposes the M3, M4, M5, and M6 resources when that generation retires. If M6-session resource initialization or target-format preflight fails, initialization fails through the existing cleanup and application fallback path.

The Raw-first Native regression on `chrome-native-webgpu` / Three.js r186 started with both required flags enabled and the independent M4/M5 research flags disabled. It mounted one native WebGPU adapter generation, published a contentful Raw frame with M4/M5 resources ready but no optical passes, exercised Focus Loupe and viewport-change requests, then completed Raw→M6 and M6→Raw→resize→M6 without fallback or retry consumption. A deliberately held M6 queue discarded an older request and completed only the latest accepted request. At the low-quality test layout, the source target remained 204×163 and the half-scale gather targets were 102×82; the viewport changes produced new request identities even though those nominal target dimensions did not change in that run. The separate M6 resize regression continues to cover a 394×315 displayed output with a 256×205 internal target.

The adapter provisions nine M5 color targets plus two M4 color targets for an M6-capable Raw-first session. At the measured 204×163 source and 102×82 gather sizes, those RGBA attachments have a nominal uncompressed color-storage estimate of 2,529,600 bytes (about 2.412 MiB): M4 uses 12 bytes per source pixel; five full-resolution M5 targets use 52 bytes per source pixel; four half-resolution M5 targets use 48 bytes per gather pixel. This estimate excludes the existing M3 scene color and depth attachments, backend padding, and driver allocation overhead. It describes M4/M5 resources provisioned for the session, not an M6 presentation target: M6 itself still adds zero render targets or color-attachment bytes and retains its existing single fused fullscreen presentation draw.

The Native failure control injects an initialization error after a real M5 Far target allocation, then verifies confirmed adapter cleanup, no completed WebGPU frame, and fallback to the existing WebGL host. The handoff and measured IDs are in [GROUND_GLASS_M6_REVIEW_FIX_1_REPORT.json](GROUND_GLASS_M6_REVIEW_FIX_1_REPORT.json). M6 remains `architecture-partially-implemented` and `quality-unqualified`; this review fix does not establish physical grid alignment, an M6 output pixel oracle, photographic quality, or production readiness.

## M6C — Native alpha readback and output contract

M6C adds a development/test-only capture that renders the existing M6 display scene and exact presentation material into a temporary `RGBA8Unorm`, `NoColorSpace` target. Allocation requires the development build, Raw pilot flag, M6 presentation flag, test-seam flag, explicit fixture control, and exact Architecture Rise scene. The capture runs in the adapter operation queue after submitted work completes, reads only sample rows through `readRenderTargetPixelsAsync`, rejects stale request/generation/source/presentation/size/mode/crop identities, restores renderer state, and disposes the owned target in `finally`. Normal frames allocate no alpha target and perform no M6C readback.

Three.js r186 reported the actual presentation material as `transparent=false`, `opacity=1`, `NormalBlending`, `alphaTest=0`, and `premultipliedAlpha=false`. Its `colorNode` expression returns `source.a`, but the opaque node-material path writes alpha one. The native fixture confirmed stored alpha one for every source-alpha swatch, including zero, partial values, and one, with a transparent clear value of zero. The capture reused the material instance that produced the M6B presentation evidence; it did not use a transparent diagnostic material or altered blending state.

The native matrix covered neutral, reduced and increased throughput, natural `parallel-cos4` illumination, centered and shifted circles, conic coverage, combined effects, Raw/Upright, centered/panned Focus Loupe, and an actual target resize. All required samples were measured; expected RGB and measured RGB matched at the RGBA8 target, while the source-alpha preservation error was maximum `1` and RMSE `0.645378`. The visible browser canvas remains opaque. Full measurements and request/input identities are in [GROUND_GLASS_M6C_ALPHA_CONFORMANCE_REPORT.json](GROUND_GLASS_M6C_ALPHA_CONFORMANCE_REPORT.json); method and limitations are documented in [GROUND_GLASS_M6C_ALPHA_CONFORMANCE.md](GROUND_GLASS_M6C_ALPHA_CONFORMANCE.md).

M6C's decisions are `alpha-observable-contract-different`, `rgb-regression-passed`, `final-output-partial`, `architecture-partially-implemented`, `quality-unqualified`, and `production-webgpu-disabled`. A diagnostic `NoBlending` variant was reverted after the independent M6B RGB oracle recorded maximum channel error 87 codes and RMSE 12.9577 on its partial-alpha patch. Resolving the material/output contract requires a separately reviewed change that retains the existing RGB result. M5Q thresholds and Q1–Q7 remain unchanged; M7 has not started.

## M6D — Opaque final presentation output contract

M6D selects an opaque final-output contract for the current development-only Architecture Rise pilot. M5 Far stores alpha one. M5 Near alpha carries optical coverage only until `createGroundGlassResearchCompositeNode()` consumes it once in `Far.rgb * (1 - coverage) + Near.rgb * coverage`; that completed linear-RGB composite writes alpha one and is the M6 input (`m5-research-composite`). M6 does not read Near coverage or blend Far/Near again. Its coverage, natural-illumination, and throughput gains affect RGB; the normal WebGPU canvas remains opaque.

The implementation preserves the TSL `source.a` expression. That expression describes the pre-material color value, not the stored output: the actual opaque `MeshBasicNodeMaterial` with `transparent=false`, `opacity=1`, and `NormalBlending` writes alpha one. The explicit CPU helper `finalizeGroundGlassOpaquePresentationRgba()` describes the expected opaque target without overwriting `outputLinearRgba`, which remains the pre-material reference value. No `NoBlending` workaround, material change, RGB algorithm change, or normal-frame GPU readback was introduced.

On the committed implementation source `b5fc75513797707f969813dbcbe89fc892626c23`, Native Chrome r186/WebGPU rendered the production M5 research-composite TSL node into an RGBA16F target for Near coverage 0, 0.25, 0.5, 0.75, and 1. All five measured RGBA values matched the independently expected blend exactly and alpha was one. The probe ran on an already-mounted renderer only after the registered Architecture Rise M5 composite had completed; the registered capture and controlled probe shared the request, channel, scene, and generation identity. Native registered M6, M6B physical/RGB, M6C alpha, Raw-first/lifecycle, M5Q, and production-preview checks remain separate evidence categories. The compact current run is in [GROUND_GLASS_M6D_OUTPUT_CONTRACT_REPORT.json](GROUND_GLASS_M6D_OUTPUT_CONTRACT_REPORT.json); historical M6C and M6B reports are unchanged.

The decisions are `opaque-presentation-contract-conformant`, `final-output-conformant`, `architecture-implemented` for the exact registered development-only Architecture Rise pilot boundary, `quality-unqualified`, and `production-webgpu-disabled`. The M6B physical overlay result remains controlled-fixture scoped: the registered Architecture Rise scene itself still has a decorative grid and does not claim a physical film grid. This scoped M6 completion does not claim other scenes/materials, multi-device support, production parity, or photographic fidelity. M7 may begin only after this PR is reviewed and merged; M7 implementation is not part of M6D.
